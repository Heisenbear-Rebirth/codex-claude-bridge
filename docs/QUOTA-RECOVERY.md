# 额度中断与自动继续

Codex、Claude Code 因订阅额度耗尽而结束工作轮次时，管理页显示 **等待额度**。此状态阻止空闲阈值和强停阈值触发维护，普通协作消息保留在队列中。

## 自动检测和继续

沿用会话已有的自动管理开关（页面上的“自动管理”）。启用后，管理器每分钟读取原生额度；如果项目已经重启，需先在“待确认接续”弹窗确认原会话，才会允许发送继续提示；确认可用额度后，向原会话提交一次继续消息。关闭开关会取消尚未发送的自动继续请求。

- Codex 使用当前 App 连接的只读 `get_usage_limits`，读取所有已报告的额度窗口。
- Claude 使用原 CLI 进程的 `get_usage`，传入 `skip_behaviors: true`，不扫描其他会话的行为或成本历史。
- 5 小时窗口恢复后，已知周额度或模型额度仍满时继续等待。重置时间仅用于显示，时间到了不等于确认恢复。读取失败、缺少必要额度字段或未知限流原因不会发送继续消息。
- 发送前再次核对原会话实例、失败轮次、模型、思考强度、权限和人工输入。新实例须以原生记录核对同一失败轮次，才能重新绑定；设置变化、人工停止、原生目标、子任务或待处理输入仍会阻止自动继续。

发送意图先写入项目内的管理数据库。服务重启及不确定响应不会导致重复发送。继续后再次受限会延后检测，逐次增加等待间隔，最长 15 分钟。`submitted` 表示原生接口确认已提交，不表示业务任务已经完成。

### 原生状态与排队输入

额度检测与发送继续消息分别判断。已发现额度中断、但原生轮次记录正在同步或仍有待处理输入时，管理器继续读取额度，并显示当前等待原因；只有确认原生状态允许接续，才发送一次继续消息。

- Claude 根据原生 `command_lifecycle` 及匹配当前输入编号的回显，识别已被同一轮消费的追加输入。轮次结束不再把本地排队计数当成“下一轮已经开始”；尚未确认的输入仍保留并阻止自动续跑。
- Codex 合并两套轮次记录时，使用共同轮次或原生时间戳确认先后顺序。顺序尚不明确时保留限额证据、等待同步，不触发压缩，也不据旧轮次发送继续消息。
- 页面根据已保存的开关状态显示“自动管理已开启”、等待原因或需要重开面板的提示；“上次上下文维护”与额度恢复分开显示，重置时间带日期并注明是上次报告的时间。

这些 Claude 状态修复需要在当前任务结束后正常重开已接入面板一次。Codex 的修复随管理服务更新生效，无需重开 Codex。已确认失败并暂停的维护记录在管理服务重启时保留原原因、回执和队列。

在 **提示词设置 → 额度恢复** 编辑继续消息，可使用 `{{sessionId}}`、`{{client}}`。默认提示要求保留原任务约束，核对已完成操作，从未完成处接续。既有提示词配置会补上此项默认值。

## Codex 给已限额的 Claude 发消息

按接收方 Claude 的状态处理，发送方 Codex 的额度不会决定这条消息是否能被 Claude 执行。

- 已识别 Claude 限额时，消息保存在 Cooperation 的队列中。投递前也会核对接收端当前状态，避免管理页快照稍有延迟就把消息误标为已发送。
- Claude 原本空闲、本次协作消息才首次触发限额时，会把原生额度错误关联到这条实时消息，进入等待额度状态。历史消息重放不能触发自动唤醒。
- 接收方开启自动管理后，确认额度恢复，先使用 **额度恢复** 提示词向原会话发送一次继续请求，再释放等待中的消息。已经交给 Claude 的消息不重复投递；后续积压消息按原顺序发送。
- “继续任务”模板用于上下文维护完成后的接续；此场景使用独立的“额度恢复”模板。接收方关闭自动管理时，不发送自动继续提示。

隔离的实际 wrapper、管理服务与协议子进程验证了“首次 peer 消息限额 → 管理快照滞后时仍保留后续消息 → 自定义继续提示一次 → 消息按顺序投递”，并保持原 Claude 进程。证据：`.cooperation/verification/peer-quota-native.txt`。未向真实业务会话发送测试消息或耗尽账号额度。

反向的 **Claude → Codex** 同样按接收方状态处理。Codex 通过最新原生轮次的结构化额度错误识别中断，不依赖 Claude 的输入观察机制。投递前会重新读取 Codex 状态；即使管理页快照尚未更新，也会将尚未发送的消息留在队列中。接收方启用自动管理且原生状态允许接续时，确认额度恢复后使用同一项“额度恢复”提示词发送一次继续请求，保留原模型与思考强度，然后按顺序释放积压消息。

该方向的隔离测试使用实际 Codex IPC 协议适配器与模拟原生端点，覆盖首次消息触发限额、快照滞后、99% 上下文时仍不压缩、自定义继续提示一次、原生设置继承及消息顺序。证据：`.cooperation/verification/codex-peer-quota-protocol.txt`。这项管理服务端调整无需重开 Codex。

## 接入与边界

退出、关机及不同启动顺序的完整处理见 [重启恢复](RESTART-RECOVERY.md)。新版 Claude 接入会在项目内保存限额状态，重开后结合原生历史核对；管理器保留未知发送结果，不因新实例出现而解除队列保护。

Claude 需要在合适时机正常重开已接入的面板一次，加载新版 wrapper。管理器会暂停旧 wrapper 的自动维护，防止它继续把额度中断当成空闲；不会强行关闭正在工作的客户端。新版只能根据自己观察到的原生事件识别失败轮次，不能补造旧进程中未观察到的中断证据。

若额度耗尽发生在交付、压缩或恢复上下文阶段，系统保留维护锁及消息队列，显示“需要处理”。额度恢复后，在管理页核对当前维护阶段再继续；不会跳过回执或自动重复压缩。

Claude 的一般限流错误也会阻止压缩，但只有明确的订阅额度窗口拒绝才能自动继续。仅有额度警告、宽限期或最终成功的轮次不会被当作额度强制中断。此功能不购买额度、不修改付费设置、不切换账号，也不发送模型探测消息。

## OpenCode

OpenCode 当前轮次的结构化 HTTP 429 会暂停压缩与排队投递。管理服务重启后也需确认接续，但目前没有统一的可核验额度查询，因此不能自动判断额度恢复；需在原会话处理后继续。

## 验证记录

本机验证了 Codex Desktop 26.928.3736.0 的真实只读额度接口；Claude 2.1.280 的原生结构已通过本地安装代码核对，使用实际 wrapper 可执行程序及协议测试进程验证了额度查询、压缩阻断和原进程单次继续。自动化测试覆盖两端的恢复、去重、人工介入、未知结果和再次受限。

隔离 Chrome 验证等待状态、重置及检测时间、额度提示词预览/保存/刷新，以及桌面和 390px 布局。证据保存在项目 `.cooperation/verification/quota-full-tests.txt` 和 `quota-browser.json`。没有通过耗尽真实账号或向业务会话注入错误来验证 5 小时额度恢复；这部分真实等待恢复链路尚未实测。

2026-10-02 修复验证：全套 **239 项通过**。实际 wrapper 和隔离管理服务完成“工作中追加两条输入 → 原生确认同轮消费 → 限额结束 → 读取额度 → 一次自定义继续消息”，原子进程保持不变、追加输入未重发。实际 Codex IPC 适配器验证了混合轮次限额记录的等待、同步及单次接续。证据为 `.cooperation/verification/quota-state-before.txt`、`quota-state-full-tests.txt`、`quota-state-browser.json`；浏览器覆盖开关即时反馈、历史维护说明、旧接入升级提示与 390px 布局。
